Scope & method

Everything below comes from reading the actual source files in this repository — no assumptions, no invented features. Two things are worth stating up front because they shape every other section:

Dead code excluded

There are two parallel backend trees: frontend/server/src/* (the one actually wired into the running app via frontend/server/createApp.ts) and a root-level src/* with an almost identical file list. The root copy is missing lib/prisma.ts, services/partyOverrides.ts, services/excelSectionNav.ts, and converter/tesseractExtractor.js — i.e. it predates the Prisma override layer and OCR support. No script in either package.json touches it. The root README.md calls it "backend/, a legacy standalone copy," but no backend/ folder exists on disk — this is that legacy copy, just not renamed. It is excluded from every section below as dead code, per instructions.

Deployment config: not enough evidence

The git root is actually D:/CA-RMHStaffPortal, a monorepo holding several sibling projects. Its render.yaml configures a Docker service named ca-rmhstaffportal with no reference to this sub-app, so it cannot be treated as this project's own deploy config. This app's only concrete deployment evidence is vite.config.ts's preview.allowedHosts entry (bank-statement-analyzer-ws8z.onrender.com) and its render:build/render:start npm scripts — enough to say "runs as one Node process on Render," not enough to describe the exact service topology.

01

Project purpose

Converts an Indian bank statement — native PDF, password-protected PDF, or a scanned/photographed PDF or image — into a party-wise transaction ledger: every transaction resolved to a real counterparty (a person, a business, or a bank-system event like a sweep or settlement), grouped, totalled, and exportable into a full set of CA-style due-diligence reports.

What problem does it solve?

Manually reading a bank statement PDF to build a party-wise ledger — who paid whom, how much, how often, which entries are salary/EMI/bounce/statutory-tax noise — is slow and inconsistent when done by hand across many statements and staff. This tool automates extraction (including OCR for scans) and counterparty resolution (a genuinely messy text problem: UPI handles, bank reference codes, OCR spacing errors), while still giving a human final say over the grouping before anything is exported.

Who would use it?

The application accepts applicantName, entityType, pan, and loanType as analysis inputs — fields that only make sense in a lending/credit-appraisal or accountancy due-diligence context, not a personal-finance app. It is branded "RMH.PLA — Party Ledger Analyzer" and is mounted as one tool inside a larger internal system: a code comment in site-chrome.tsx notes the router's basepath is "its own /__tools/one-page-party-analysis/ mount prefix" inside a staff portal, with a "Back to Dashboard" link out to that portal's root. Combined with the monorepo's name (CA-RMHStaffPortal), the strong inference is an internal tool for staff at a Chartered Accountancy / financial-advisory practice, used while reviewing a client's or loan applicant's bank statements. (This is inference from strong contextual evidence — the app itself never states its audience in these words.)

02

Architecture

Frontend

React 19 rendered through TanStack Start (a file-based-routing SSR framework built on Vite, using h3 as its server-request abstraction) with TanStack Router for routes and TanStack Query's QueryClient instantiated in router.tsx. Styling is Tailwind CSS v4 plus a local shadcn/ui-style component layer (frontend/src/components/ui) built on Radix UI primitives. Recharts renders the numeric charts implied by lib/dailyMetrics.ts's chart-tick helpers; Framer Motion drives the upload-row and progress-step animations.

Backend

An Express 5 app (frontend/server/createApp.ts) — but it is never run as its own server. In dev, a custom Vite plugin (vite-plugin-api.ts) mounts the Express app as Connect middleware inside Vite's own dev/preview server. In production, frontend/server/apiFetch.ts wraps the same Express app with h3's fromNodeMiddleware to produce a Fetch-API-shaped handler, which frontend/src/server.ts (the actual deploy entry point) tries first on every request before falling through to TanStack Start's own SSR handler. One Node process, one port, serves the React app and /api/* + /health.

Database

SQLite (a single file, frontend/server/data/party-ledger.db), accessed through Prisma 7 using its newer prisma-client generator plus the @prisma/adapter-better-sqlite3 driver adapter — a pure JS/native-binding path with no Prisma query-engine binary. Only three tables exist (Party, TransactionAssignment, PartyAuditLog) and they store only manual corrections and their audit trail — the computed analysis report itself is never written to this database (see Engineering Decisions §1).

APIs

RouterMounted atResponsibility
convertRouter/api/convertStateless one-shot: upload one PDF, get one Excel workbook back. No storage, no party resolution.
analysisRouter/api/analysis/*The stateful lifecycle: create analysis, fetch by id, edit party/transaction overrides, list parties & audit log, download per-module Excel.

Notable libraries

  • pdfjs-dist — PDF text-layer extraction.
  • tesseract.js + @napi-rs/canvas — OCR path: canvas renders PDF pages to bitmaps (via pdfjs-dist again) for statements with no usable text layer, or for image uploads.
  • exceljs — every Excel workbook the app produces.
  • multer — multipart upload handling with a disk-storage backend.
  • Groq's chat-completions API, called with a raw fetch (no SDK) — optional LLM-assisted party-name resolution.
  • puppeteer-core is a declared dependency and is ssr-externalized in vite.config.ts, and the README lists "Chrome or Edge (for master PDF export)" as a prerequisite — consistent with a headless-print PDF export path, but no call site for it was found in the files read this pass. Flagged as not enough evidence to describe precisely.

Why this architecture makes sense

This is an internally-used, moderate-traffic staff tool, not a public multi-tenant SaaS product. Running the API and the SSR app as one process removes an entire category of problems (CORS, two ports, two deploy targets, environment drift) that would otherwise exist for zero benefit at this scale. SQLite-via-driver-adapter mirrors the same instinct: the durable data is small, per-analysis, and doesn't need a managed database server — the explicit cost of that choice is that it doesn't horizontally scale across multiple instances without a shared volume for the `.db` file, which is an acceptable trade for an internal tool.

03

System design — request flow

End-to-end path from dropping a PDF on /upload to seeing (and exporting) the party ledger.

  1. Upload
    upload.tsx collects one row per file (password, "scanned" checkbox) and on submit builds a FormData with parallel statement / passwords[] / scanned[] fields, POSTed to /api/analysis (lib/api.ts's createAnalysis).
  2. Multer intake
    Express's shared statementUpload (defined in convert.routes.ts, reused by analysis.routes.ts) streams each file to server/uploads/<uuid>.<ext>, preserving the original extension — the converter decides PDF-vs-OCR by extension, so a stripped extension would break that decision.
  3. Extraction (per file)
    convertPdfToStatement() picks a stage: ocr if the file is an image or was flagged "scanned," otherwise pdf. The pdf stage uses pdfjs-dist to pull text runs per page and clusters them into lines by Y-coordinate (±3px tolerance), sorted left-to-right within a line. The ocr stage renders each PDF page to a PNG via @napi-rs/canvas at 2.2× scale (or uses the image file directly) and runs it through a cached tesseract.js worker, reconstructing lines from Tesseract's block/paragraph/line/word geometry.
  4. Silent OCR fallback
    If the fast pdf path parses to zero transactions, the whole extraction is retried once as ocr — this is how a photocopied/scanned statement that was saved as an ordinary PDF (no real text layer) still gets read, without the user having to know to tick "scanned" themselves.
  5. Row parsing
    parseStatement() extracts account-info fields via label regexes, then parses transaction rows: a Bank-of-Baroda-layout check runs first (unconditionally), otherwise the generic date/amount-column heuristic parser runs; if that yields zero rows, four more specialized layout parsers are tried in order — Society Savings Compact → South Indian Bank → Society/Co-op → generic Columnar OCR.
  6. Give up cleanly
    Zero transactions after every fallback throws NO_TRANSACTIONS_FOUND, mapped to an HTTP 400 with a clear message rather than a generic 500.
  7. Normalize & classify
    analyzeBankStatements() (analysis/report.ts) flattens every uploaded statement's transactions into one date-sorted list (normalizeTransactions), computing debit/credit/direction, a first-pass regex-based party guess, payment mode, and category per row, then builds month-by-month metrics (buildMonthMetrics).
  8. Optional AI overlay
    applyAiPartyResolution() can call Groq's chat-completions API (batched ≤60 rows / ≤45,000 JSON characters, with a recursive halving retry on batch failure) to layer aiParty, aiCounterPartyLedger, and aiPartyConfidence onto each transaction — an additional signal, not a replacement for the deterministic party field.
  9. Store & respond
    The finished report is kept in an in-memory Map (analysisStore.ts) under a generated id like PLA-2026-6117723, and returned directly in the POST response — the report the client sees first is never re-fetched at this point, it's the same object just computed.
  10. Analyzing screen
    The client saves {id, report} into analysis-report-store.ts and navigates to /analyzing, which shows a fixed-cadence (650ms/step), purely cosmetic progress list — the real work already finished server-side — while it re-fetches GET /api/analysis/:id once to guarantee a fresh copy, then redirects to /report.
  11. The one page
    /report immediately redirects to /report/transactions-summary — the app's single real report screen, matching its "one-page" name. It renders TransactionSummaryTable, which runs buildPartyLedger() client-side (a parallel copy of the server's grouping logic, in lib/transactionSummary.ts) over the already-fetched transactions, so period-filter changes don't need another network round trip.
  12. Manual correction
    Renaming/merging/splitting/excluding a party or transaction calls one of the PATCH/POST/DELETE /api/analysis/:id/... endpoints. The server persists the override in SQLite (partyOverrides.ts), writes a PartyAuditLog row, re-applies every stored override onto the original in-memory report via hydrateReport(), and returns the updated report — which the client saves back into the store, and every subscribed screen re-renders via useLatestReportVersion()'s useSyncExternalStore hook.
  13. Export
    ModuleExcelButton calls GET /api/analysis/:id/excel/:module[?period=monthly&monthKey=...]. The server re-hydrates the report, optionally scopes it to one calendar month (scopeReportByMonth), and ExcelGeneratorService.generateModuleExcel() builds the requested workbook (or every module combined, for the master report) and streams it back as an .xlsx with a generated client/bank/period filename.

08

Engineering decisions

1 · In-memory analysis store, SQLite only for overrides

Problem
Need somewhere to hold a freshly computed report so later GET/PATCH calls can find it by id, plus durable storage for human corrections.
Approach
A module-level Map<string, AnalysisRecord> holds the report; Prisma/SQLite is used only for Party/TransactionAssignment/PartyAuditLog.
Alternatives
Persist the whole report JSON to Postgres/SQLite too; use Redis or a job queue for multi-instance durability.
Trade-off
Simplest possible build for a single-instance internal tool — but report data doesn't survive a restart or scale past one instance, and the Map has no eviction, so it grows for the life of the process.

2 · Bank-agnostic heuristic parser with layout-specific fallbacks

Problem
Dozens of Indian banks format statements differently, and some only ever appear as scans.
Approach
One generic geometry/regex parser for "well-behaved" tabular PDFs, with a short ordered list of specialized parsers (Bank of Baroda, two OCR-only cooperative/society layouts, South Indian Bank, generic columnar-OCR) tried only when the generic one returns zero rows.
Alternatives
A parser-per-bank registry keyed by detected bank name; a fully ML/LLM-based table extractor.
Trade-off
Keeps the common case fast and free of an LLM call, while still covering known problem layouts — but a new unusual bank layout means writing a new bespoke parser file, and the fallback order is a hand-maintained if/else chain, not a scored/pluggable registry.

3 · Deterministic entity resolution by default, LLM as an optional overlay

Problem
A bank narration string is inherently messy (OCR noise, UPI VPA suffixes, bank/rail codes, boilerplate); resolving "the real counterparty" is a fuzzy problem.
Approach
A large, carefully tuned rules engine does extraction + Levenshtein/token-similarity clustering entirely offline; groqPartyResolver.ts optionally asks an LLM for a second opinion, merged in as separate aiParty/aiCounterPartyLedger/aiPartyConfidence fields, never a replacement.
Alternatives
LLM-only extraction; a supervised classifier trained on labeled narrations.
Trade-off
Works fully offline/free with no API key, and every result is reproducible and debuggable — at the cost of a large hand-maintained surface (noise-word sets, merchant alias lists, bank-code maps) that needs updating whenever a new pattern shows up in real statements.

4 · Overrides layered on top of, never baked into, the auto-detected report

Problem
A user must be able to correct a wrong party grouping without losing the ability to reset back to what the algorithm originally said.
Approach
TransactionAssignment.originalParty snapshots the auto-detected label the first time a transaction is touched; hydrateReport() applies only customParty/excludedFromLedger on top of an otherwise-untouched base report on every read, instead of mutating the report in place.
Alternatives
Mutate the in-memory report directly on every edit; store a full "final" report snapshot per edit.
Trade-off
Clean undo/reset and an accurate audit "before" value, at the cost of re-running the hydrate join on every single report read (cheap here, but assumes both the base report and its override count stay small).

5 · Party-grouping logic duplicated between server and client

Problem
The on-screen summary table needs to group/label parties identically to the Excel exports, without round-tripping to the server on every render or filter change.
Approach
The client ships its own copy of the grouping/canonicalization logic (lib/transactionSummary.ts, structurally near-identical to the server's entityResolution.ts) and re-runs it locally over the transactions already embedded in the fetched report.
Alternatives
Have the server pre-compute the grouped summary and send only that; extract a shared package used by both.
Trade-off
Fast, dependency-free re-grouping when the period filter changes — at the cost of two copies of genuinely complex fuzzy-matching logic that have to be kept in sync by hand, with no shared module boundary enforcing it.

6 · A "live proxy" data layer instead of prop-drilling or a state library

Problem
Many report components need read access to the current analysis report, and appear (from the code's shape) to have first been built against fixed-shape data.
Approach
data/reportData.ts exports every "data" binding (applicant, momSummary, transactions, …) as a Proxy that transparently reads the live report out of analysis-report-store.ts on every property access — components import what looks like a static value but always read live state.
Alternatives
React context or a Redux/Zustand store threaded through every component; refactor every component to take the report as a prop.
Trade-off
Lets many components stay decoupled from prop-drilling without a state-management dependency — at the cost of a genuinely unusual "magic import" pattern a new contributor has to discover, and an ESLint exhaustive-deps suppression anywhere it's read inside useMemo/useEffect (confirmed, commented, in report.transactions-summary.tsx) since the real dependency is a version counter, not the proxy reference itself.

7 · Only an id, never the full report, survives a hard reload

Problem
Keep report state simple across in-session navigation, without silently serving a stale full-report blob after a hard refresh.
Approach
saveLatestReport keeps the full report only in a module-level JS variable; the localStorage write is just the analysis id. A hard reload always finds an empty in-memory report and re-fetches the full report via GET /api/analysis/:id.
Alternatives
Cache the full report JSON in localStorage/IndexedDB for true offline reloads.
Trade-off
Always-fresh data after any server-side edit, and no localStorage size/staleness problem — at the cost of a network round trip on every hard refresh, and total data loss if the server process restarted and the in-memory store lost that id (compounding decision #1).

8 · Cosmetic fixed-cadence progress UI, not real server progress

Problem
Statement analysis (parse + OCR fallback + optional LLM call) can take anywhere from ~1s to tens of seconds, but POST /api/analysis is one synchronous request/response with no streaming channel.
Approach
The client already has (or fetches once) the finished report; /analyzing's step list advances on a fixed 650ms setInterval purely for perceived progress, capped at the last step once the real fetch resolves.
Alternatives
SSE/WebSocket progress events from the conversion pipeline; a polling job-status endpoint.
Trade-off
Much simpler than real progress plumbing, and good enough since the upload step already blocks on the real work — but the visible "% complete" is cosmetic, so it can't tell a user why a genuinely slow OCR run is slow.
09

Security

Mechanisms in place

  • Upload allowlisting — multer's fileFilter accepts only PDF/JPG/PNG/TIFF (by mimetype or extension), capped at 25MB.
  • No persistent raw uploads — files are written under a random UUID filename (never the user-supplied name) and deleted in a finally block after every request, success or failure.
  • Explicit password-error handling — pdfjs-dist's PasswordException is mapped to clear PASSWORD_REQUIRED/INVALID_PASSWORD codes rather than surfacing a raw parser crash.
  • No leaked internals — a single catch-all Express error handler normalizes every thrown error to {code, message}, and the production SSR path explicitly replaces h3's default JSON error body / stack trace with a generic branded error page, logging the real error server-side only.

Gaps — evidenced, not assumed

  • No authentication anywhere in this code. Any request to /api/analysis/:id/* only needs the id string. The Prisma schema itself says outright that "this sub-app has no auth/session concept yet" (the unused actor field on PartyAuditLog). Since this is mounted behind a staff portal, real auth may exist one level up — not enough evidence in this codebase to say either way.
  • No rate limiting on /api/analysis or /api/convert, both of which do CPU-heavy work (PDF parsing, OCR, an external LLM call) per request.
  • Guessable analysis ids — PLA-<year>-<last 7 digits of Date.now()> is sequential, not cryptographically random; combined with no auth, a recent analysis id is enumerable.
  • Unbounded in-memory store — the analysisStore Map never evicts; every analysis, completed or failed, stays in server memory for the life of the process (a resource-exhaustion surface under sustained use, not just a hygiene nit).
  • Ad hoc .env discovery — groqPartyResolver.ts's readEnvFile() walks up to two parent directories looking for a .env file rather than relying solely on process.env; worth confirming this can't pick up an unintended file in a shared hosting layout.
  • No centralized request-schema validation on the party-management endpoints — just ad hoc typeof x === "string" checks. Reasonably safe since Prisma parameterizes queries, but zod (a declared dependency) isn't used here.

Performance

Optimizations that exist

  • buildPartyLedger() explicitly merges what used to be two separate O(n·uniqueParties) fuzzy-clustering passes into one, per its own comment — both the on-screen table and every Excel module were doing that expensive work twice.
  • OCR is cached and reused: Tesseract's model data is cached to disk (server/data/tesseract-cache) and the worker is created once (module-level workerPromise), not per request.
  • The Groq call is batched (≤60 rows or ≤45,000 JSON characters per request) instead of one HTTP call per transaction, with a recursive halving retry so one bad row doesn't fail an entire batch.
  • OCR (the expensive path) only runs when needed: explicitly scanned files, image files, or a PDF that parsed to zero transactions on the fast text-layer path.
  • The client re-derives the grouped party summary locally instead of round-tripping to the server on every period-filter change.

Likely bottlenecks (inferred from code, not measured)

  • generateMasterReport() runs all ~21 module generators sequentially, synchronously, in one request — a large statement produces a very large workbook with no evidence of streaming or background job handling.
  • The unbounded in-memory analysisStore is also a performance concern over long uptime, not just a security one (see above).
  • pickCanonicalLabel() compares every unique auto-detected party label against every other (Levenshtein + token similarity) — quadratic in the number of unique party names, usually small relative to transaction count but growable on a very high-diversity statement.
  • OCR runs page-by-page sequentially (await inside a for loop in extractScannedFile), not in parallel — a multi-page scanned statement is proportionally slow.
  • No caching by file hash — re-uploading an identical statement re-runs the entire parse/OCR/LLM pipeline from scratch.

STAR story

Situation
Staff reviewing Indian bank statements for loan/credit or accountancy due-diligence work had to manually read PDFs — often scanned, password-protected, or laid out differently by different banks — to build a party-wise ledger of who paid whom, a slow and inconsistent process across statements and staff.
Task
Build an internal tool that takes any statement (native PDF, scanned PDF, or a photographed/scanned image) from any Indian bank, automatically resolves every transaction's real counterparty despite messy narration text (UPI handles, OCR noise, bank reference codes, boilerplate), and produces both an interactive on-screen ledger and a full set of CA-standard Excel reports a human can still correct before finalizing.
Action
I designed a layered pipeline: a bank-agnostic geometry/heuristic PDF parser with a Tesseract OCR fallback for scans, plus five specialized fallback parsers for known problem layouts; a deterministic entity-resolution engine that strips banking boilerplate and reference codes, scores candidate counterparties per narration segment, and clusters near-duplicate labels using Levenshtein distance and token similarity, entirely offline; an optional LLM overlay (Groq) that proposes a second-opinion normalized name/category per transaction, merged in rather than trusted blindly; a Prisma/SQLite override layer so a human can rename, merge, split, or exclude parties/transactions afterward with a full audit trail, without ever losing the original auto-detected label; and a 21-module Excel export engine (Flags & Risk, CAM Analysis, Bounce & Penal, Loans & EMI, Salary, Trade Credits/Debits, Circular Flows, and more) plus a combined master workbook.
Result
A single upload flow now takes a statement — in whatever condition it arrives in, from any of several Indian banks — straight to a corrected, exportable party ledger and a full CA report pack, with every manual correction preserved and auditable, and the core pipeline working fully standalone with no external API dependency, with the LLM step as a purely additive enhancement on top. (No measured time/cost-savings figures are in evidence — this states delivered capability, not a claimed metric.)

Concepts demonstrated

Integrated SSR + API server via a custom Vite plugin

Where: the entire request-routing layer. File: frontend/vite-plugin-api.ts, frontend/vite.config.ts.

A Vite plugin hooks configureServer/configurePreviewServer to mount an entirely separate framework (Express) as middleware inside Vite's own dev and preview servers, so one npm run dev serves both the SPA/SSR app and a REST API on the same origin and port. This is the mechanism that lets the rest of the app pretend "frontend" and "backend" are the same server, which they are, at runtime.

Interview angle: Why mount Express as Vite middleware instead of a Vite proxy to a second process? What's different between the dev-time plugin path and the prod fetch-handler path?

Node-middleware ⇄ Fetch API adapter pattern

Where: production request handling. File: frontend/server/apiFetch.ts (h3's fromNodeMiddleware), frontend/src/server.ts.

Modern SSR runtimes (TanStack Start's server entry) speak the standard Fetch API (Request/Response), while Express is built on Node's older (req, res, next) middleware signature. h3's adapter bridges the two, letting the same Express app that runs as Connect middleware in dev also answer fetch-shaped requests in the production handler.

Interview angle: What does fromNodeMiddleware actually have to translate between the two calling conventions (streaming body, headers, status)?

Driver-adapter Prisma (no query-engine binary)

Where: database access. File: frontend/server/src/lib/prisma.ts, frontend/server/prisma/schema.prisma.

Prisma 7's prisma-client generator plus @prisma/adapter-better-sqlite3 replaces the classic Prisma architecture (a separate Rust query-engine binary the Node process talks to over a pipe) with a pure-JS driver adapter wrapping better-sqlite3 directly — fewer moving parts to deploy, at the cost of being newer/less battle-tested than the classic engine.

Interview angle: What problem do Prisma driver adapters solve relative to the classic query-engine architecture?

Layered fallback parsing strategy

Where: statement-to-transactions parsing. File: frontend/server/src/converter/parser.ts.

Rather than a single "smart" parser or a full per-bank config system, one generic geometry/regex parser handles the common case, and a short, explicitly ordered chain of specialized parsers is tried only when the generic pass returns nothing — a simple, debuggable strategy pattern implemented as a plain if/else chain instead of a formal interface.

Interview angle: Why check Bank of Baroda's layout unconditionally, first, rather than as a zero-result fallback like the other four?

OCR pipeline with PDF-to-raster rendering

Where: scanned-statement support. File: frontend/server/src/converter/tesseractExtractor.js.

A PDF with no usable text layer is rendered page-by-page to a bitmap (via pdfjs-dist's canvas rendering + @napi-rs/canvas, a native binding, at 2.2× scale for legibility) and each page image is fed to a persistent, cached Tesseract worker, whose block/paragraph/line/word geometry is reassembled into the same line-based shape the native-text extractor produces — so everything downstream (the parser) doesn't know or care which extraction path ran.

Interview angle: Why 2.2× render scale specifically, and what would happen to OCR accuracy at 1×?

Deterministic, rules-based entity extraction

Where: turning a narration string into a counterparty name. File: frontend/server/src/analysis/classification.ts, entityResolution.ts.

A cascade of regex-driven checks (known merchant aliases, bank-event patterns, self-transfer patterns, UPI-hyphen parsing, cash-deposit parsing, SI-mandate parsing) each score a candidate counterparty and confidence; the highest-confidence result wins. This is essentially hand-built lightweight NLP for one narrow domain, not a generic NLP library.

Interview angle: Why compute a confidence score at all if the pipeline is fully deterministic — what is it actually used for downstream?

Fuzzy string clustering (Levenshtein + token similarity)

Where: merging OCR-mangled or partial-name variants of the same party. File: analysis/entityResolution.ts (pickCanonicalLabel, isNamePartialVariant, tokensMatch).

After extraction, raw party labels are clustered by exact key match, token-set similarity, single-token aliasing, and a same-first-token partial-name check with edit-distance tolerance — hand-rolled, not a library — to decide, e.g., that "ZEENAT RAMZAN HASNANI" and "MR RAMZAN HASNANI" are the same person without ever merging two different people who merely share a first name.

Interview angle: Walk through why the first-token-exact-match guard in isNamePartialVariant exists.

LLM-as-overlay integration pattern

Where: optional AI-assisted party naming. File: analysis/groqPartyResolver.ts, routes/analysis.routes.ts (applyAiPartyResolution).

The LLM call is batched, retried by recursive halving on failure, and its output is written into separate fields (aiParty, aiCounterPartyLedger, aiPartyConfidence) rather than overwriting the deterministic party field — a pattern that keeps a probabilistic, external, rate-limited dependency strictly additive to a system that must keep working without it.

Interview angle: What would go wrong if the Groq response overwrote party directly instead of being stored separately?

Snapshot-based override / undo data model

Where: the manual-correction feature. File: prisma/schema.prisma (TransactionAssignment.originalParty), services/partyOverrides.ts.

The very first time a transaction is touched, its current auto-detected label is copied into a plain string field. Every later "reset" or "reassign to original" reads that snapshot instead of re-deriving it — a simple, robust undo mechanism that doesn't depend on the auto-detection algorithm being deterministic or stable over time.

Interview angle: Why snapshot a plain string here instead of just re-running the extraction function on demand to "recompute" the original party?

Audit logging as a first-class side effect

Where: every mutation in the party-override system. File: services/partyOverrides.ts (logAudit), PartyAuditLog model.

Every create/rename/delete/reassign/exclude/restore operation writes a before/after PartyAuditLog row in the same function that performs the mutation, rather than as a separate cross-cutting concern — simple, but means the audit trail is only as complete as each function remembering to call logAudit.

Interview angle: What are the risks of implementing audit logging this way versus, say, a database trigger or event-sourcing approach?

Idempotent hydrate/projection pattern

Where: merging overrides onto the base report. File: services/partyOverrides.ts (hydrateReport).

Instead of mutating the stored report as edits happen, every read re-derives a "view" by applying the full current set of TransactionAssignment rows onto an untouched copy of the base report. This is the same idea as a projection in event sourcing, at a much smaller scale — the base data plus a set of changes, recombined on demand.

Interview angle: What would you need to add to make this scale if a report had a very large override count?

Proxy-based reactive data binding

Where: connecting "static-looking" imports to live client state. File: src/data/reportData.ts.

JavaScript Proxy get-traps intercept every property access on an exported "data" object and redirect it to a live lookup into the report store — letting existing component code that imports momSummary or transactions keep working unchanged while the underlying data source moved from static fixtures to a real API. A genuinely unusual pattern worth understanding deeply if you inherit this codebase.

Interview angle: What are the risks of a Proxy-based data layer versus explicit props or a context hook?

External-store subscription via useSyncExternalStore

Where: the client's report cache. File: src/lib/analysis-report-store.ts.

React's useSyncExternalStore subscribes components to a plain module-level variable (not Redux/Zustand/Context) via a simple listener-set + version-counter, which is exactly the API React ships for bridging non-React state into the render cycle correctly (including concurrent rendering).

Interview angle: Why useSyncExternalStore instead of a custom useEffect + useState subscription?

File-based routing with a redirect-only index

Where: the report section's URL structure. File: src/routes/report.index.tsx, report.transactions-summary.tsx, report.tsx.

/report itself renders nothing — it immediately redirect()s to /report/transactions-summary, the single real page, while the shared report.tsx layout route provides the header/period-selector shell every nested page renders inside via <Outlet />. A deliberately thin routing layer for what is, by name and design, a one-page report.

Interview angle: Why keep /report as a real (redirecting) route instead of just linking to /report/transactions-summary directly everywhere?
